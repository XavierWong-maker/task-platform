# ADR-0008：阶段 11 DAG 工作流设计

## 背景
阶段 1–10 的任务都是独立的：一个 Job 一次运行。阶段 11 要回答：多个任务有先后依赖时，
怎样保证顺序、并行执行互不依赖的分支、失败时下游怎么办、能否只重做失败的部分。
验收标准（蓝图 8.12）：能运行至少 5 节点的 ETL DAG，并正确处理失败节点与下游依赖。

## 决策
1. **图结构在构造时校验**：`WorkflowDefinition` 构造成功就保证合法（节点唯一、依赖存在、无自依赖、无环）。
   Kahn 算法按层输出，同层节点互不依赖；排不完说明有环，再沿依赖链走出具体的环路径用于报错。输出顺序按声明顺序，结果可复现。
2. **规则是纯函数**：`ready_nodes` / `nodes_to_skip` / `derive_workflow_status` 只读"节点名 -> 状态"映射，
   与执行器无关，可单独测试。节点终态不可再转换；工作流状态由节点状态**派生**，不单独维护。
3. **失败传播**：只要有上游处于 FAILED / SKIPPED / CANCELED，PENDING 的下游就 SKIPPED（按拓扑顺序一遍得到传递闭包）。
   没有依赖关系的并行分支不受影响，继续运行。整体状态：全成功 SUCCESS；有成功也有失败/跳过 PARTIAL_FAILED；
   没有任何成功 FAILED；有取消 CANCELED（在蓝图的五个状态之外新增）。
4. **引擎线程模型**：调用 `run()` 的线程是协调线程，只有它修改节点状态和触发 `on_update`，无需加锁；
   runner 池驱动节点（含重试循环），handler 池交给 `execute_attempt`。两个池大小都是 `max_parallel`，
   避免任务在池里排队而被算进超时。
5. **每次尝试一个新的 `CancelToken`**：`execute_attempt` 超时时会取消令牌，复用会让下一次重试被误判为已取消。
   节点级取消由 `_NodeControl` 桥接（同时打断重试等待）。
6. **节点内重试复用 `execute_attempt` 与 `RetryPolicy`**，同一节点各次尝试共享 run_id（与 Scheduler / Worker 一致）。
7. **持久化**：定义整体以 JSON 存储（总是整体读写，不拆表）；运行记录带**定义快照**；节点运行单独一张表。
   节点每次尝试仍是普通的 `job_executions` 行，日志仍在 `job_logs`，因此已有的 `logs` / API 直接可用。
   引擎提供 `on_attempt` 钩子，每次尝试结束后立刻落库并取走该次尝试的日志（否则重试多次的日志会全部算到最后一次）。
   `workflow_runs.status` 是便于过滤的冗余快照，每次更新由节点状态重新算出。
8. **重试 / 重跑 = 创建新的工作流运行**（`parent_run_id` 指向来源），来源运行保持不变。沿用的节点复制来源结果并标记
   `reused`，不再执行。`retry` 沿用所有 SUCCESS 节点；`rerun X` 重置 X 与 X 的全部下游，其余原样沿用（包括 FAILED 的兄弟分支），
   且 X 的上游必须全部成功。重放使用来源运行的定义快照，不读取也不覆盖 `workflows` 表里的当前定义。
9. **迁移 0006 不用 batch 模式**：SQLite 的 batch 会重建表，而本项目开启了外键，重建父表会级联删除子表数据。
10. **DAG 版 ETL**：阶段之间通过工作目录里的文件交接数据，每个阶段只依赖上游文件和配置、结果确定，因此可安全重跑。
    复用 `pipeline.py` / `quality.py` 的业务逻辑；测试保证全部成功时三个输出文件与单体任务逐字节相同。
    故障注入用环境变量 `TASK_PLATFORM_ETL_DAG_FAIL_STAGE`。
11. **入口**：CLI `workflow register|list|run|retry|rerun|history|show`（Ctrl+C 转成取消令牌）；
    API 位于 `/api/v1/workflows*` 与 `/api/v1/workflow-runs*`，运行类接口与 ADR-0003 一致，同步执行。

## 替代方案
- 在同一次运行里把失败节点重置为 PENDING 再跑：被否决，要放宽终态不可变的状态机，且会改写历史。
- 在节点之间用内存传递数据：被否决，节点是独立的 Job，需要能单独重跑；文件交接让每个阶段的输入输出可检查。
- 把定义拆成节点表和依赖表：被否决，定义总是整体读写，拆表只增加删除重建的复杂度。
- 引入 Airflow / Prefect / Celery canvas：超出本阶段范围，目标是理解依赖调度与失败传播的原理。
- 单独存储并更新工作流状态：被否决，派生值不会与节点状态不一致。

## 影响
- 新增或修改节点状态规则，要同步 `workflow_state` 的测试；修改定义 JSON 结构要考虑已保存的快照。
- 新增 ETL 阶段：加到 `STAGES` 与 `jobs/etl_dag_jobs.py`，并保证阶段可重跑、结果确定。
- 修改 `etl_dag` 输出格式时，与单体任务的逐字节对比测试会失败，提醒两处保持一致。

## 已知限制
- **没有崩溃恢复**：引擎进程崩溃后，工作流运行停在 RUNNING，只能重放已结束的运行，没有 `workflow recover`；
  节点进入 RUNNING 时也没有提前落库（没有使用 `on_started`）。
- 引擎在单进程里执行，**没有经过队列 / Worker**（未与阶段 8 的 Redis 队列集成）；工作流没有调度触发（调度规则作用于 Job，不作用于工作流）。
- API 的运行接口同步占用请求线程，无法通过 API 取消；取消只能通过 CLI 的 Ctrl+C。
- 节点之间没有数据传递机制，靠约定的工作目录；同一目录同时只应有一次运行，并发运行需使用不同的 `TASK_PLATFORM_ETL_OUTPUT_DIR`。
- 运行前会检查**所有**节点的 Job 都存在且 handler 已注册（包括将被沿用的节点）；API 的 `PUT` 不检查 Job 是否存在，运行时才报错。
- 取消发生在重试等待期间时，最后一次尝试记录会停在 RETRYING。
- 历史迁移 0003 使用 batch 模式，对已有执行日志的旧库升级时，在开启外键的 SQLite 上可能级联删除 `job_logs`；升级旧库前请备份。
